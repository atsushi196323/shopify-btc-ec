# ADR 1: Shopify チェックアウトへの組み込み方式

- ステータス: 確定（2026-10-08、W2 の拡張の E2E で確認）
- 日付: 2026-10-01

## コンテキスト
Shopify のチェックアウトに独自の決済方法を出すには Payments App が必要で、
これは Shopify の審査を受けるパートナー向けの仕組み。カスタムアプリでは使えない。
今回は開発ストアのカスタムアプリとして作る。

## 決定
**手動決済方法と、Thank you / 注文状況ページの Checkout UI Extension を組み合わせる。**
- 管理画面で手動決済方法「Bitcoinで支払う」を作る。注文は支払い待ちのまま確定する。
- `orders/create` Webhook で BTCPay の invoice を作る。拡張から問い合わせた時点で未作成なら、冪等に作る（[ADR 5](0005-invoice-creation-dedup-and-orphan-recovery.md)）。
- 拡張で支払いリンクと状態を表示する。
- Settled になったら Admin GraphQL の `orderMarkAsPaid` で支払い済みにする。

## W1 で確認したこと（2026-10-02）
- 開発ストア `bitcoin-ec`（Basic プラン、JPY）に手動決済方法「Bitcoinで支払う」を作り、テスト注文が「支払い待ち」で確定することを確認した。
- Thank you / 注文状況ページの拡張は Basic プランでも使える。

## 未検証事項（W2 の最初に30分で区切って確認する）
- **拡張からアプリの API を呼べるか**: Checkout UI Extension の `network_access = true` には、アプリ単位の承認が必要。
  CLI 4.8 で作った Dev Dashboard のアプリには承認の画面がなく、公開時にエラーになる例が報告されている（2026年9月時点で未解決）。
  最小の Thank you 拡張で、開発プレビューからアプリの API を呼べるかを確かめる。
  呼べない場合は、invoice の作成時に支払いリンクを注文のメタフィールドに書き、拡張はそれを読むだけにする案を検討し、ここに記録する。
  → **2026-10-04 に確認済み（下記）。当初の案のまま進める。**
- **保護された顧客データ**: カスタムアプリには Level 1・2 が最初から付いていて、申請は不要とされている。
  `read_orders` / `write_orders` を `shopify.app.toml` に足し、`orders/create` の Webhook を登録できるかで確かめる。

## W2 で確認したこと（2026-10-04、拡張の通信）
最小の Thank you 拡張（`network_access = true`）から、アプリの `GET /api/extension/ping` を呼んだ。
- **開発プレビューでは呼べる**: 本物の Thank you ページで、セッショントークン付きのリクエストに 200 が返った
  （`authenticate.public.checkout` で検証。`sessionToken.dest` は `bitcoin-ec.myshopify.com`）。
  CLI 4.8.3 でも、開発プレビューの段階では承認を求められなかった。
- **公開（`shopify app deploy`）での承認は未確認**: MVP とデモは開発プレビューで動かすので、ここで止める。
  公開が必要になったときに承認の問題が出たら、メタフィールドを読む案に切り替える。
- 実装で使うこと:
  - 拡張からアプリの URL は `process.env.APP_URL` で得る（CLI がビルド時に埋め込む。開発中はトンネルの URL）。
  - CORS とプリフライトは `authenticate.public.checkout` と `cors()` が扱う。ただし**認証失敗の 401 には CORS ヘッダが付かない**ので、
    拡張からはステータスではなく通信エラーに見える。拡張は通信エラーを「時間をおいて再表示」として扱う。
  - curl などの User-Agent はボットとみなされ 410 になる（ライブラリの仕様）。手で叩くときはブラウザの User-Agent を付ける。
- 開発プレビューの注意（手動 E2E・デモの手順に書く）:
  - ブロックの target（`purchase.thank-you.block.render`）は、置く場所を決めないと表示されない。
    設定なしで表示される静的な target（`purchase.thank-you.customer-information.render-after`）を使う。
  - 拡張は、URL に `?dev=<トンネル>/extensions` が付いたカートから始めた注文でしか読み込まれない。
    CLI のプレビュー用リンクはストアの最初の商品をカートに入れるので、在庫切れだと進めない（開発ストアのギフトカードは販売を続ける設定に変えた）。

## W2 で決めたこと（2026-10-08、拡張の UI）
- `extensions/thank-you/src/Checkout.jsx` は、拡張 API の表示状態をそのまま描く。checkout link は `AWAITING_PAYMENT` のときだけボタンで出す（別タブで開く）。
- 問い合わせ直し:
  - `PREPARING` と通信エラー（5xx・429・401 の例外など）は 3 秒ごと、続けて 20 回まで。超えたら「時間をおいて再表示」を出す。
    支払いの表示がすでにあれば、上流が失敗している可能性が高いので間隔は 30 秒のままにし、表示も消さない。
  - 400・404・410（不正な注文 ID、ボット判定など）は問い合わせ直しても変わらないので、すぐにやめる。
  - まだ変わりうる状態（支払い待ち・入金確認中・期限切れ）は 30 秒ごと、同じ状態のまま 60 回（約30分）まで。状態が変わったら数え直す。
    期限切れも含めるのは、期限後の入金で「ショップから連絡します」に進むことがあるため（design.md 4章）。
    サーバーは問い合わせのたびに Admin API を、支払い待ちなら BTCPay も1回呼ぶので、間隔を長めに取った（リンクを使い回して BTCPay を呼ばない最適化はしない）。
    変わりうる状態の表示のまま問い合わせをやめたら、表示は残して「最新の状態は再表示して確認」を添える。
  - 知らない状態や、リンクのない支払い待ちが返ってきたら、通信エラーと同じに扱う。拡張は状態の一覧を手で持つので、サーバーに状態を足したら拡張にも足す。
- **待っている間と失敗したときの表示は、手動決済方法（`selectedPaymentOptions` の `type` が `manualPayment`）の注文にだけ出す**。
  Bitcoin の注文かどうかは拡張 API が答えるまで分からず、カードで払った客に「Bitcoin でのお支払い」を出さないため。
  拡張から見えるのは支払い方法の種類と、セッションごとの handle だけで、名前は見えない。このため**手動決済方法は「Bitcoinで支払う」だけ**という前提を置く
  （銀行振込などを足すと、その客にも待っている間の表示が出る）。
  最初の応答の前（LOADING）と `NOT_APPLICABLE` は何も表示しない。
- 手動の E2E（2026-10-08、注文 #1010〜#1017）で確かめたこと:
  - Thank you ページの `orderConfirmation.order.id` は **`gid://shopify/OrderIdentity/<数字>`** で届いた（型の説明の Order の GID ではない）。
    サーバーは数字を同じにした Order の GID にそろえて Admin API で取れることを確かめた（ADR 4）。
  - `selectedPaymentOptions` は Thank you ページでも埋まっており、「Bitcoinで支払う」は `type: "manualPayment"` で届いた。
  - 支払い待ちの注文で、拡張 API が `AWAITING_PAYMENT` と checkout link を返し、拡張が表示した。
  - ¥10 の注文は BTCPay が dust の下限未満として invoice の作成を断り、拡張は「準備中」の後に「再表示してください」を出した（design.md 9章の既知の制限）。
- 開発プレビューの注意（手動 E2E・デモの手順に書く）:
  - **`shopify app dev` を起動し直した直後は、拡張が読み込まれない**ことがあった。拡張のファイルを保存し直し、ログに「Updated dev preview」が出てから注文すると読み込まれた。
  - トンネル（quick tunnel）は途中で名前が引けなくなることがある。そのときは拡張の問い合わせも `orders/create` も届かないので、`shopify app dev` を起動し直す（URL が変わるので、`?dev=` 付きのリンクも作り直す）。
  - `?dev=` 付きのリンクは、CLI の開発サーバーの `/extensions/<拡張の uuid>/<target>` が転送する先（`/cart/<variant>:<数量>?dev=<トンネル>/extensions`）で、数量を変えれば請求額を変えられる。
  - プレビューのリンクをストアのトップにする（`shopify app dev --checkout-cart-url /`）と、拡張は読み込まれない（2026-10-15）。
    トップから商品・カートへ移る間に `?dev=` が外れるため。注文と invoice の作成は正常に進むので、拡張が何も表示しないことでしか気づけない。
    `--checkout-cart-url` を使うときは、CLI の決まった形式（`/cart/<variant>:<数量>`）で在庫のある商品を指定する。
  - regtest の invoice の期限は 180 秒（bootstrap.sh。60 秒では手で確かめる時間が足りず延ばした。ADR 10）なので、ボタンから支払う確認は注文から3分以内に行う。W3 の Webhook の処理ができるまで、BTCPay で期限が切れても拡張は支払い待ちのまま表示する。

## 検討した代替案
- **ヘッドレス + Draft Order**: ストアフロントまで自作する必要があり、工数のわりに決済の設計力は伝わりにくい。
- **注文確認メールに支払いリンクを載せるだけ**: 状態を表示できず、体験が悪い。

## 結果
- 「注文は先に確定し、支払いは後から来る」という非同期の流れになる。期限切れ、再発行、期限後の入金などの論点が生まれる。
- Shopify 標準のチェックアウトをそのまま使える。
- 公式 BTCPay プラグインとほぼ同じ方式なので、自作した部分との比較で説明しやすい。
