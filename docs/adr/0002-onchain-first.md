# ADR 2: オンチェーンを優先し、Lightning は stretch

- ステータス: 承認（2026-10-04、ドメインを支払い方法に依存しない形で実装）
- 日付: 2026-10-01

## コンテキスト
BTCPay は1つの invoice でオンチェーンと Lightning の両方を受け付けられる。
作業時間は限られている（MVP は約56時間）。

## 決定
**MVP はオンチェーンだけにする。Lightning は stretch。**

## 理由
- オンチェーンには、承認数、過少払い・過払い、期限後の入金、RBF・二重支払いなど、
  **状態遷移と異常系の論点が多い**。バックエンド寄りの評価者に示したい設計力が最も出る。
- regtest では `generatetoaddress` でブロックを自由に進められるので、テストを決定的に書ける。
- Lightning は全額か失敗かの二択で状態は単純だが、regtest でノード・チャネル・流動性を用意する手間が大きい。

## 結果
- ドメインモデルは、支払い方法に依存しない形にしておく。Lightning は試行の支払い方法として後から追加できる。
